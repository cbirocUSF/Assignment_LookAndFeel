Developing This Website

The assignment was to build the static front end of a data-driven site for an assigned content theme, in my case an educational institution. I chose scholarships and financial aid as the subject because it is data that students actually act on: an award amount, a deadline and a GPA threshold are the three things an applicant needs, and they are also the fields an aid office has to keep current. That gave the site a clear purpose and made the CRUD page something more than a demonstration form.

I started by sketching the four required pages and deciding what data each one needed. Rather than hard-coding figures into each page, I put the full scholarship catalog in a single file, js/data.js, and had every page read from it. The home page calculates its summary totals from that array, the Manage Scholarships page works against a copy of it, and the Analytics page aggregates it into chart series. Because there is only one source of data, the dollar figures on the home page, the rows in the table and the bars on the charts cannot drift apart.

The layout came next. I used Bootstrap 5 for the responsive grid, the navigation bar, the form controls and the modal dialog, then wrote a custom stylesheet on top of it so the site would not look like an untouched template. The palette is built from two brand colors, #367588 and #2f4f4f, with a gold accent that ties back to the institution's mining history. Declaring those colors as CSS custom properties in :root meant I could restyle the entire site by changing four lines. The hero illustration and the crest are hand-written SVG rather than photographs, which keeps the page fast and avoids broken image links.

The hardest part was the CRUD page. My first version used separate forms for adding and editing, which duplicated validation logic. I reworked it so one form handles both operations, switching modes based on whether an editingId is set, and the page got noticeably simpler. I also replaced a browser confirm() dialog on delete with a Bootstrap modal, both because it looks consistent with the rest of the site and because a blocking dialog is a poor experience. The data lives in memory only, so a refresh restores the sample catalog, which is the behavior the assignment calls for in a static mock.

Technologies Used

  • HTML5 — semantic structure for all four pages, with a shared navigation bar and footer.
  • CSS3 — a custom stylesheet using CSS custom properties for the brand palette, plus media queries for small screens.
  • JavaScript (ES5 syntax) — DOM manipulation, event handling, array filtering and aggregation, written without a framework.
  • Bootstrap 5.3.3 — responsive grid, collapsible navbar, form validation styling, alerts and the delete confirmation modal.
  • Chart.js 4.4.1 — the three visualizations on the Analytics page, loaded only on that page so the other three stay light.
  • SVG — the hero illustration and institutional crest, authored by hand so they scale to any screen size.
  • Visual Studio Code — the editor used to write and test every file.
  • Git and GitHub Pages — version control and static hosting for the finished site.

What I Learned

Three things stand out. First, deciding where the data lives is a design decision, not a detail; moving the catalog into one file solved problems on three pages at once. Second, a framework like Bootstrap gets you to a responsive layout quickly, but the difference between a template and a finished site is the custom work layered on top of it. Third, performance is mostly about restraint: keeping Chart.js off the pages that do not need it, drawing the artwork in SVG instead of loading photographs, and writing plain JavaScript rather than pulling in a library for work the browser already does.
